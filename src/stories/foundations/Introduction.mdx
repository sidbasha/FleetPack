# FleetPack Component Library

This is the live, interactive catalog for the **Base Module** — the standalone
Angular component set every FleetPack screen (FAM, FCM, TQual, Dashboard) is
built from. It exists so design and engineering can review a component's
anatomy, variants, and states **without a Figma file and without running the
full app**.

It replaces static "component list" documents (screenshots + descriptions)
with something a browser can actually render, control, and diff against
`main` on every PR.

## How this maps to the design-system deliverable

The FleetPack Design System engagement calls for, per component:

| Deliverable | Where it lives here |
|---|---|
| **Definition** — what it is, what it solves | The JSDoc comment above each component class, rendered on its **Docs** tab (via Compodoc) |
| **Anatomy** — visual parts | The rendered story canvas |
| **Variants** — sizes, density, styles | Named stories per component (e.g. `Primary`, `Secondary`, `Ghost`, `Danger`) |
| **States** — hover, disabled, loading, error, empty | Dedicated `Disabled` / `Loading` / `Error` / `Empty` stories, plus the **Controls** panel to toggle any input live |
| **Behavior** — click, keyboard, apply/reset | Component outputs, documented on the Docs tab; exercised live in the story |
| **Accessibility** — contrast, focus, keyboard | `@storybook/addon-a11y` runs automated checks on every story (see the **Accessibility** tab) |
| **Engineering handoff** | This *is* the engineering artifact — the selector, inputs, and outputs shown here are the real Angular API, not a mockup of it |

## Organization

- **Base / Actions** — `<base-button>`
- **Base / Forms** — text input, textarea, select, checkbox, radio group, toggle, date picker, search input
- **Base / Feedback** — alert, badge, trend, progress bar, skeleton, loading, empty state
- **Base / Navigation** — breadcrumbs, tabs, dropdown menu
- **Base / Overlays** — drawer, modal, tooltip
- **Base / Cards & Containers** — KPI card, sparkline
- **Base / Tables & Data** — table, paginator
- **Widgets** — the `WidgetConfig`-driven layer every FAM screen composes pages from: KPI grid, chart (ng2-charts), ranked list, table (legacy `ColumnDef` adapter over `<base-table>`), the panel-chrome wrapper (`<fam-dynamic-widget>`), and the 6-column responsive grid (`<fam-dynamic-page>`)
- **Layout** — app shell pieces with no service dependencies (currently: `<fam-sidebar>`)
- **Shared** — domain components built on top of Base (e.g. `fam-state-legend`)

### What's *not* here yet, and why

`<fam-topbar>`, the FAM/FCM/TQual/alarm-explorer route components, and the
domain chart components that read live state directly (`<fam-state-heatmap>`,
`<fam-activity-gantt>`) all `inject()` real app services or signal stores
(`AuthService`, `ApiService`, `FilterStore`, `UptimeStore`) rather than taking
data as `@Input`/`input()`. Storying them means either standing up stub
providers that mimic those services' shapes, or the real ones with mocked
HTTP — a separate, larger effort from documenting the presentational
component library, and one the design-system SOW explicitly scopes out
("module pages are not the deliverable"). Deliberately deferred, not missed.

## Source of truth

Every story imports the **real component classes** from `src/app/base`
(barrel: `src/app/base/index.ts`) — nothing here is redrawn or approximated.
If a component's Angular API changes, its story either updates to match or
fails to compile, which is the point.

A second, in-app reference still exists at **`/dev/base`** — a single page
that exercises every Base component against live signal state and a real
event log. Use that route to see components wired together in a workflow;
use *this* catalog to review one component in isolation, drive every input,
and check accessibility.

## Foundations

Tokens now have both a source and a set of pages: `src/styles.css` is the
actual token source (a three-tier Tailwind v4 `@theme` block — primitive →
semantic → component, see **Foundations → Token Architecture**), and every
cross-cutting rule that isn't a component has its own documented page:

- **Foundations / Token Architecture** — the three-tier system and naming convention every other page (and every future component) builds on
- **Foundations / Color** — the audited KLA Vivid Electric palette, the 4-step error ramp, and how Machine State / Alarm Severity re-key onto it
- **Foundations / Typography** — the Instrument Sans / Inter / JetBrains Mono type scale
- **Foundations / Spacing & Sizing** — the 12-step 4px spacing scale and control/overlay sizing table
- **Foundations / Radius & Elevation** — the 5-step radius and 5-level elevation scales
- **Foundations / Grid & Layout** — breakpoints, the 12-column grid, and container rules
- **Foundations / Iconography** — Material Symbols Outlined, the size scale, and the icon-by-category reference
- **Foundations / Density & Themes** — row-density modes; Light is the only theme this project ships, no dark mode or theme switcher

## What's still open

The foundations layer above is additive by design — it introduces new
`sp-*`/`r-*`/`display-*`/`body-*` utilities and re-points a handful of
already-global `styles.css` classes (`.panel`, `.btn-primary`, `.chip*`, …)
to the new semantic tokens, but it does **not** yet touch any individual
Base component's own template/class bindings. Restyling each Base component
(button, forms, table, modal/drawer, nav, alert/toast, badge/tag/chip,
tooltip, cards/KPI) to the new spec, and building the components that don't
exist yet (segmented control, combo box, stat bar, state heatmap, Gantt
timeline, and the rest of the chart family), is deliberately deferred to a
follow-up pass — see each component's own story once that work lands.
